# Deploy Later to Cloudflare

For the optional owner-only ChatGPT connector, follow [CONNECTOR.md](CONNECTOR.md). Its separate Access AUD is set as `mcpAccessAudience` in the ignored deployment config; omitting it disables MCP without changing website authentication.

The reference deployment uses `later.xplo8e.com`. Its deployment history is in [DEPLOYMENT-RUN.md](DEPLOYMENT-RUN.md); the identifiers there belong to that installation, not yours. Use your own account, database, Access applications and GitHub OAuth app.

## Before you start

You need Node 22.13 or newer, a copy or fork of this repository, a GitHub account, and a Cloudflare account with Workers, D1 and Zero Trust Access available. Run `npm ci` from the repository root to install the locked project-local tools. You do not need to install Wrangler globally or connect GitHub to Cloudflare Builds for this manual deployment flow.

For a custom hostname such as `later.your-domain.com`, have an active Cloudflare DNS zone for `your-domain.com` in the account you will deploy to. Use a dedicated, unused hostname. A Worker Custom Domain binds the hostname to the Worker and manages its DNS/certificate; a CNAME pointing at a workers.dev address is not a substitute. If the hostname already has a CNAME, resolve that conflict deliberately before creating the Custom Domain. Do not delete records serving another application. See [Worker Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/).

**Current limitation:** the account settings are configurable, but the hostname is still hard-coded. Before deploying a fork to another domain, its maintainer must separately adapt `scripts/deploy.mjs`: both the custom-domain route and `vars.APP_ORIGIN`. The origin must be the exact HTTPS origin without a path or trailing slash. The base `wrangler.jsonc` also contains the reference origin and owner display values. This guide does not change those files. Do not add an invented `domain` field to `deployment.config.json`; the script does not read it. Editing only the generated `wrangler.production.json` will not work because the script regenerates it.

The hostname examples below mean your chosen hostname once that prerequisite is complete. Do not try to deploy someone else's hostname. Existing branding and the metadata self-host exclusion also reference the original owner; review those separately if personalizing a fork.

## Configuration files

| File | What belongs here | Git handling |
| --- | --- | --- |
| `deployment.config.json.example` | Placeholder shape for deployment settings | Committed template; no real credentials |
| `deployment.config.json` | Your account ID, D1 identity, Access team/AUD, owner email and optional MCP AUD | Ignored; create locally from the template |
| `wrangler.jsonc` | Base Worker name, bindings, local database placeholder and display defaults | Committed; not a production credential file |
| `wrangler.production.json` | Production bindings generated by the deployment script | Ignored; review it, do not maintain it by hand |
| `.dev.vars.example` / `.dev.vars` | Local development authorization flag | Template committed; real local file ignored |
| `dist/` / `.wrangler/` | Generated bundles and local runtime/database state | Ignored |

The GitHub OAuth client secret belongs in Cloudflare's identity-provider settings. Wrangler stores its own login credentials outside the project. Neither goes in these JSON files, source code, issue reports or commits. Account IDs, database IDs, client IDs and AUD tags are identifiers, not passwords; they still need to identify your installation correctly. Keep access tokens, refresh tokens and signed Access cookies private.

## 1. Account and database

Use the Cloudflare account containing your domain zone. In Cloudflare One / Zero Trust, complete organization setup and choose a team name. Record the resulting `https://YOUR_TEAM.cloudflareaccess.com` address. This is the Access team domain, not your website domain or GitHub username. Dashboard navigation can change; look for Zero Trust Settings and Integrations / Identity providers.

Authenticate Wrangler through its supported sign-in flow:

```bash
npx wrangler login
npx wrangler whoami
```

Check that `whoami` lists the intended account. Copy its account ID, not the domain's zone ID. If you have several accounts, explicitly select the target for database creation:

```bash
CLOUDFLARE_ACCOUNT_ID=YOUR_ACCOUNT_ID npx wrangler d1 create later
```

Replace `YOUR_ACCOUNT_ID` with the real ID. Record the returned database name and UUID. Use another unused database name if `later` already exists; do not accidentally attach someone else's library or create a replacement for a database you already use. Keep the Worker binding named `DB`, regardless of the database's name. Leave the local-only placeholder in the base config alone; the deployment script supplies the real binding.

Check the current Workers, D1 and Access quotas/pricing for your selected plans. This script does not enforce a spending cap, and a domain registration is separate from hosting.

## 2. GitHub identity provider

GitHub authenticates the library owner. It does not need repository access for this login flow, and the Cloudflare account email does not need to equal the GitHub owner's email.

1. Sign in to your GitHub account. Open **Settings > Developer settings > OAuth Apps > New OAuth App**. Create an OAuth App, not a GitHub App or personal access token.
2. Give it a recognizable name such as `My Later login`. Enter the URLs below, substituting your actual Cloudflare team name.
3. Register the app and generate a client secret. Copy the client ID and store the secret securely; do not put the secret in the repository.
4. In Cloudflare Zero Trust, open **Integrations > Identity providers**, add **GitHub**, enter that client ID in the App ID / Client ID field and the secret in Client secret, then save.
5. Use the identity-provider test flow to sign in with the intended GitHub account. Note the email Cloudflare reports; use that exact identity in both the owner policy and `ownerEmail`. Do not substitute a GitHub handle or guess a noreply address.

GitHub OAuth application URLs:

- Homepage: `https://YOUR_TEAM.cloudflareaccess.com`
- Callback: `https://YOUR_TEAM.cloudflareaccess.com/cdn-cgi/access/callback`

The callback goes to Cloudflare Access, not to `/api`, `/app`, or the ChatGPT connector. Follow the [Cloudflare GitHub identity-provider guide](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/github/) if the dashboard labels differ.

## 3. Protect the private paths

Before publishing, go to **Access controls > Applications**, create a **Self-hosted** application such as `Later private library`, and add your website hostname with paths `app` and `api`. Check coverage of both exact paths and descendants; a wildcard-only entry must not leave `/app` or `/api` unprotected. Do not protect the entire hostname, because the login page and install assets must remain public.

Required coverage on your hostname:

| Path | Access |
| --- | --- |
| `/` | Public login page |
| `/app` and `/app/*` | Owner only |
| `/api` and `/api/*` | Owner only |
| `/manifest.webmanifest`, `/icons/*`, `/sw.js`, `/offline.html`, `/assets/*` | Public static assets |

Add one **Allow** policy, for example `Later owner only`:

- **Include > Emails:** your exact email from the GitHub IdP test.
- **Require > Login Methods:** the GitHub identity provider you created.
- In the application's login methods, disable accepting all identity providers and select only that GitHub provider. Do not enable WARP authentication as an alternate route.

Keep the email and login-method conditions in those separate Include/Require groups so GitHub login alone cannot satisfy the allow rule. Access denies identities without a matching allow policy. Do not add Everyone, email-domain-wide, Bypass or Service Auth policies to the private paths.

Choose a website session duration, for example 24 hours. Review policy/global session overrides as well. This browser session is separate from the optional MCP OAuth grant. Enable HTTP-only cookies. Record the website application's AUD from its additional settings; this is not its application UUID or the GitHub client ID.

Record the application's audience (AUD) tag and Access team domain. The Worker independently verifies the assertion signature, issuer, audience, expiry and owner email. An email header alone is not accepted. See [JWT validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/) and [Access path rules](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/app-paths/).

## 4. Prepare and publish

From the repository root, copy the template once. If the local file already exists, edit it instead of overwriting it:

```bash
cp deployment.config.json.example deployment.config.json
```

Replace every placeholder:

| Field | Required value |
| --- | --- |
| `accountId` | Account ID from `wrangler whoami` / account dashboard, not zone ID |
| `databaseId` | UUID returned by `wrangler d1 create`, or the existing database's dashboard |
| `databaseName` | `later`, or the name created above |
| `accessTeamDomain` | Full `https://YOUR_TEAM.cloudflareaccess.com` origin |
| `accessAudience` | Access application AUD tag |
| `ownerEmail` | Exact permitted identity email |
| `mcpAccessAudience` | Optional, distinct MCP Access AUD from [CONNECTOR.md](CONNECTOR.md); omit the field entirely when not using MCP |

The template deliberately contains no GitHub secret, Wrangler token or hostname selector. Do not copy account/AUD/database values from this repository's deployment history. `ownerEmail` is authorization; `OWNER_NAME` and `OWNER_HANDLE` in the base config are display values only.

```bash
npm run deploy -- --prepare-only
```

Review `wrangler.production.json` before any remote deployment. Confirm the account ID, database UUID/name, exact owner email, team domain and website AUD. Check that `routes` contains your intended Custom Domain and `vars.APP_ORIGIN` matches it. If a fork still shows `later.xplo8e.com`, stop and complete the hostname prerequisite above. Keep both `workers_dev` and `preview_urls` false, and do not add `LOCAL_DEV` to production.

The current build checks refer to `dist/later/`, so leave the Worker name as `later` unless you separately adapt the script and tests. Check for an existing Worker with that name in your account before deploying to avoid replacing another service. Then deploy:

```bash
npm run deploy
```

This command checks Wrangler's login, builds with the production configuration, checks that local authorization was removed, runs the tests, applies pending migrations to the configured remote database, and publishes the compiled Worker/assets. It does not verify a real GitHub sign-in, create the OAuth app or Access policies, or seed production with design fixtures. Do not run sample SQL against the remote database. Local build/test success is not proof of a working production identity flow.

The [Cloudflare Vite guide](https://developers.cloudflare.com/workers/vite-plugin/tutorial/) explains the generated build configuration used by deployment.

## 5. Live acceptance checks

1. In a signed-out browser, `/` shows the login screen, and `/app/` requires GitHub sign-in. The private API must not return library data anonymously.
2. Sign in as the configured owner. Save a link with a note, reload, edit it, search for it, move it to Finished and export the library.
3. Verify that a different GitHub identity is denied. Confirm the alternate Workers deployment URLs are disabled.
4. Check live metadata extraction from several ordinary public websites. A metadata failure must preserve the saved URL and note.
5. On Android Chrome, open the HTTPS site, sign in, then choose Add to Home screen / Install app from Chrome's menu, or Install Later in Settings when Chrome exposes the prompt.
6. Launch the installed icon and verify standalone appearance, sign-in persistence, short and long screens, text entry with the keyboard, rotation, and external-link behavior.
7. Launch once while online, then disconnect and reload. The generic offline screen should appear. Reconnect and retry. Private notes and API responses must not be available from the service-worker cache.

PWA installation requires HTTPS or a supported loopback development origin. The current remote development preview is not evidence of a successful Android install. See [installability requirements](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable) and [the optional in-app install prompt](https://web.dev/articles/customize-install).

## Operations

For a later code update, preserve your ignored deployment config and run `npm ci` followed by `npm run deploy`. Do not recreate D1 or the GitHub OAuth app on every release. Review migrations before applying them and export important library data before changes.

Export from Settings for a user-readable snapshot. D1 recovery and backups are managed in the Cloudflare account. The delete-all action is deliberately gated by typed confirmation. Schema changes should be added as new migrations; do not edit an already applied migration.

The application is configured for one owner. Changing owners requires changing both the Access policy and `ownerEmail`, followed by deployment. No public registration or sharing is implemented.

## Setup troubleshooting

| Symptom | Check |
| --- | --- |
| GitHub callback mismatch | OAuth App callback must exactly use your Access team domain and `/cdn-cgi/access/callback` |
| GitHub succeeds but Access denies login | Compare the IdP-reported email with the exact-email policy and selected GitHub provider |
| Access allows login but Worker returns 401 | Check `ownerEmail`, website AUD and team domain; an app UUID is not an AUD |
| Worker says private access is not configured | Required Access values are missing from the deployed Worker |
| Worker says to use the private hostname | `APP_ORIGIN` does not match the requested origin; account config alone does not change it |
| DNS/TLS failure or 522 | Check the Worker's Custom Domain binding and conflicting DNS records, not just a CNAME |
| D1 permission/not-found error | Confirm Wrangler account, `accountId`, database UUID and migrations target refer to the same account |
| Connector requires daily reconnection | Check its explicit OAuth grant duration; inheriting a 24-hour app session gives a daily grant expiry |

Do not fix an authentication error by adding a Bypass policy or disabling the Worker's independent checks.
